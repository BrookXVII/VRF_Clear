# VerifyBot

VerifyBot — Telegram-бот на PowerShell для верификации пользователей в корпоративных группах. Бот получает обновления Telegram, проводит пользователя через форму верификации, управляет доступом к группам, отвечает на inline/callback-запросы и отправляет служебные уведомления.

Проект рассчитан на запуск в Windows PowerShell 5.1 или PowerShell 7+. Для параллельной обработки используются `RunspacePool` и общие хеш-таблицы очередей.

## Возможности

- верификация пользователей через Telegram Gateway;
- обработка сообщений, inline-запросов и callback-запросов;
- управление участниками групп: проверка статуса, ограничения, бан, кик и разблокировка;
- создание, отзыв и отправка приглашений в группы;
- формы для основного меню, запуска, верификации и административных операций;
- раздельные очереди получения обновлений, обработки и отправки сообщений;
- ограничение скорости отправки с учетом глобального и посекционного/чатового throttling;
- повторная отправка временно неуспешных запросов;
- структурированные логи, ошибки, отладочные записи и ротация файлов.

## Требования

- Windows PowerShell 5.1 или PowerShell 7+;
- доступ к Telegram Bot API;
- токен Telegram-бота;
- токен Telegram Gateway, если используется Gateway-верификация;
- доступ к внутреннему API, указанному в `apiUrl`, если он используется текущей конфигурацией;
- права бота на чтение сообщений и управление участниками в обслуживаемых группах;
- права на чтение и запись каталогов проекта, особенно `pbLogs` и файлов очередей.

Внешние PowerShell-модули для базовой работы проекта не требуются, однако конкретные интеграции могут зависеть от доступности внутренних API.

## Быстрый запуск

### 1. Получить исходный код

```powershell
git clone <repository-url>
Set-Location .\verifybot
```

### 2. Настроить секреты

Заполните рабочую конфигурацию в `pbSettings/BotSettings.json` или в используемом PowerShell-файле настроек. Минимально необходимы идентификатор/токен бота, `botNum`, `botCreator` и параметры, соответствующие включенным интеграциям.

Не добавляйте реальные токены в README, issues, pull request или публичный Git-репозиторий. При утечке токена его необходимо немедленно отозвать и выпустить новый.

### 3. Проверить синтаксис

Для проверки всех PowerShell-файлов:

```powershell
$parseErrors = @()
Get-ChildItem -Recurse -Filter *.ps1 | ForEach-Object {
    [System.Management.Automation.Language.Parser]::ParseFile(
        $_.FullName,
        [ref]$null,
        [ref]$parseErrors
    ) | Out-Null
}

if ($parseErrors.Count -gt 0) {
    $parseErrors | Format-List
    exit 1
}

'Syntax check passed'
```

### 4. Запустить бота

```powershell
.\pbStart\Create-Runspace.ps1
```

Точка входа инициализирует настройки, модули, очереди и worker-runspace. Затем отдельные обработчики получают обновления Telegram, обрабатывают их и передают операции в очередь отправки.

## Остановка

Для штатной остановки используйте:

```powershell
.\pbStart\pbStop.ps1
```

Этот скрипт устанавливает флаг остановки `botRun`. Также остановку можно инициировать, изменив `botRun` на `$false` в активной конфигурации. Уже выполняющиеся операции могут завершиться до полного освобождения runspace.

## Конфигурация

Основной JSON-файл — `pbSettings/BotSettings.json`. В репозитории также находятся PowerShell-конфигурации `BotSettings.ps1` и тестовая конфигурация. Перед запуском проверьте, какой файл подключает текущая точка входа.

Ниже перечислены ключи, которые используются текущей конфигурацией проекта. Значения URL, токенов и Telegram ID должны соответствовать конкретному окружению.

### Подключения и идентификация

| Параметр | Назначение |
| --- | --- |
| `appPath` | Абсолютный путь к корню проекта. |
| `apiUrl` | URL внутреннего API, используемого интеграциями проекта. |
| `botID` | Токен Telegram-бота. Секретное значение. |
| `gateID` | Токен Telegram Gateway. Секретное значение. |
| `checkToken` | Токен внутренней проверки. Секретное значение. |
| `botNum` | Числовой идентификатор бота. |
| `botCreator` | Telegram ID владельца или технического администратора. |
| `eulaUrl` | URL пользовательского соглашения или политики обработки данных. |
| `botRun` | Главный флаг работы бота. При `false` циклы должны завершиться. |
| `checkStaffRun` | Однократный сигнал запуска ночной проверки: после приёма сигнала основной процесс сбрасывает его в JSON. |
| `alertGroup` | Чат для служебных уведомлений. |
| `logSendGroup` | Управляет отправкой служебных записей в группу, если поддерживается конфигурацией. |
| `banIfNotVerified` | Определяет, блокировать ли пользователя, который не прошел верификацию. |
| `preserveOrderPerChat` | Сохраняет порядок операций отправки в пределах одного чата. |

Параметры `alertThread*` задают идентификаторы тем в `alertGroup`:

| Параметр | Назначение |
| --- | --- |

| `alertThreadUninvited` | Пользователи без приглашения. |
| `alertThreadPhoneNotFound` | Не найден телефон или связанные данные. |
| `alertThreadSystemError` | Системные ошибки. |
| `alertThreadBalance` | Уведомления о балансе Gateway. |
| `alertThreadAdded` | Уведомления о добавлении бота или пользователя. |
| `alertThreadUsersOut` | Уведомления, связанные с удалением или отсутствием пользователей. |

### Runspace и очереди

Время ожидания указывается в миллисекундах, если не указано иное.

| Параметр | Назначение |
| --- | --- |
| `inlineRunspacesMax` | Максимальное число runspace для inline-обработчика. |
| `inlineRunspacesSleepTime` | Пауза inline-обработчика. |
| `messageRunspacesMax` | Максимальное число runspace для сообщений. |
| `messageRunspacesSleepTime` | Пауза обработчика сообщений. |
| `callbackRunspacesMax` | Максимальное число runspace для callback-запросов. |
| `callbackRunspacesSleepTime` | Пауза callback-обработчика. |
| `sendingRunspacesMax` | Максимальное число worker-runspace для отправки. |
| `sendingRunspacesSleepTime` | Пауза обработчика очереди отправки. |
| `sendingMaxRetries` | Максимальное количество повторных попыток отправки. |
| `getUpdateTimeoutSec` | Таймаут long polling Telegram в секундах. |
| `getUpdateSleepTime` | Пауза между итерациями получения обновлений. |
| `checkStaffSleepTimeSec` | Пауза между проверками сигнала в отдельном Runspace (секунды). Ошибка кадрового API не лишает пользователя подтверждённого статуса; незавершённый отзыв доступа повторяется при следующем запуске проверки. |

## Архитектура

Рабочий цикл состоит из нескольких независимых частей:

```text
Telegram Bot API
       |
       v
GetUpdateScriptBlock -> очереди message / inline / callback
       |                         |
       v                         v
MessageHandler       InlineHandler / CallbackHandler
       |                         |
       +-----------> queueSendingHash
                              |
                              v
                   SendingHandlerScriptBlock
                              |
                              v
                     Telegram Bot API
```

Общие очереди и служебные хеш-таблицы передаются в runspace. Поэтому изменение структуры очереди или ключей команд может повлиять сразу на несколько worker-скриптов.

### Каталоги

| Каталог | Содержимое |
| --- | --- |
| `pbAssets` | JSON-данные групп, пользователей, справки и скрипты подготовки данных. |
| `pbForms` | Формы главного меню, запуска, верификации и административного раздела. |
| `pbHandlers` | Бизнес-логика обработки сообщений, callback, inline, базы данных и ViaBot. |
| `pbModules/Chat` | Обертки Telegram API для управления чатами и участниками. |
| `pbModules/Messages` | Получение, отправка, редактирование и удаление сообщений и медиа. |
| `pbModules/GateWay` | Взаимодействие с Telegram Gateway и проверка верификации. |
| `pbModules/Interface` | Построение кнопок и клавиатур Telegram. |
| `pbModules/Utils` | Общие функции, отчеты и логирование. |
| `pbStart` | Инициализация runspace, остановка, проверка сотрудников и worker-script blocks. |
| `pbSettings` | Конфигурации окружений. |
| `pbLogs` | Очереди и файлы логов runtime. |

### Основные точки входа

- `pbStart/Create-Runspace.ps1` — запуск и инициализация worker-ов;
- `pbStart/pbStop.ps1` — штатная остановка;
- `pbStart/GetRunspaces.ps1` — получение сведений о runspace;
- `pbHandlers/Message/MessageHandler.ps1` — обработка обычных сообщений;
- `pbHandlers/Inline/InlineHandler.ps1` — обработка inline-запросов;
- `pbHandlers/Callback/CallBackHandler.ps1` — обработка callback-кнопок;
- `pbHandlers/DataBase/RegisterUser.ps1` — регистрация пользователя;
- `pbModules/ImportModules.ps1` — импорт и инициализация модулей.

## Логирование и диагностика

По умолчанию используются три файла:

- `pbLogs/queueLogHash.json` — обычные события;
- `pbLogs/queueErrorHash.json` — ошибки обработчиков и API;
- `pbLogs/queueDebugHash.json` — отладочная информация.

При достижении `logging.maxSizeMB` файл ротируется. Количество сохраняемых архивов ограничивается `logging.keepFiles`. В дополнение к файлам обработчики могут выводить диагностические сообщения в консоль.

### Порядок диагностики

1. Проверьте, что `botRun` включен и используется ожидаемый файл настроек.
2. Проверьте синтаксис измененных `.ps1`-файлов.
3. Посмотрите `queueErrorHash.json`, затем основной лог.
4. Проверьте доступность Telegram API и внутреннего `apiUrl`.
5. Убедитесь, что бот добавлен в группу с необходимыми правами.
6. Для проблем с очередью отправки проверьте `sendingRunspacesMax`, `sendingMaxRetries`, throttling и `preserveOrderPerChat`.
7. После изменения конфигурации перезапустите процесс бота.

Не публикуйте содержимое логов без предварительной проверки: сообщения могут содержать Telegram ID, URL, внутренние адреса или данные пользователей.

## Разработка

### Добавление метода Telegram API

1. Создайте отдельный файл в подходящем каталоге `pbModules`.
2. Сохраните существующий стиль параметров и формат результата соседних модулей.
3. Подключите файл через `pbModules/ImportModules.ps1`, если он не импортируется автоматически.
4. Вызовите модуль из соответствующего handler-а или отправьте действие в очередь отправки.
5. Проверьте обработку ошибок и повторных попыток.

### Изменение handler-а

Перед изменением проверьте ближайший ScriptBlock в `pbStart/pbScriptBlocks`. Он определяет, какие параметры и очереди передаются в handler. Нельзя менять имена ключей очереди только в одном файле: producer и consumer должны использовать одинаковый контракт.

### Проверка одного файла

```powershell
$errors = @()
[System.Management.Automation.Language.Parser]::ParseFile(
    (Resolve-Path .\path\to\script.ps1),
    [ref]$null,
    [ref]$errors
) | Out-Null

$errors
```

Для изменений в многопоточном коде дополнительно проверьте остановку runspace, очистку ресурсов, повторную обработку ошибок и отсутствие несинхронизированной записи в общие хеш-таблицы.

## Безопасность

- Храните токены вне публичного репозитория и не добавляйте их в логи.
- Ограничьте права файла настроек и каталогов с runtime-данными.
- Не включайте в диагностические сообщения полные заголовки авторизации, токены и персональные данные.
- Смените токены, если они попали в Git, чат, issue или общий лог.
- Проверяйте права бота в группах после изменения `banIfNotVerified` и логики управления участниками.

## Известные особенности

- Проект использует как JSON, так и PowerShell-файлы настроек; перед запуском важно определить активный источник конфигурации.
- Файлы runtime-очередей и логов могут изменяться во время работы бота и не должны редактироваться вручную без понимания формата.
- Параллельные обработчики требуют осторожности при изменении общих очередей и команд остановки.
- Параметры throttling и порядок сообщений влияют на задержку, пропускную способность и поведение Telegram API.
